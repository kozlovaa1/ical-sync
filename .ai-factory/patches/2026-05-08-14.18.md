# Allow future Node LTS runtimes and safer Docker verification

**Date:** 2026-05-08 14:18
**Files:** `package.json`, `package-lock.json`, `README.md`, `docs/getting-started.md`, `docs/testing.md`, `.ai-factory/DESCRIPTION.md`, `.ai-factory/PLAN.md`, `AGENTS.md`
**Severity:** low

## Problem

The Node runtime migration still constrained `engines.node` to `>=22 <23`, which rejected newer Node LTS runtimes even though the project only needs Node 22 as a minimum baseline. Runtime verification docs also showed Docker bind-mount commands without an explicit user, which can leave root-owned or otherwise inaccessible files in the working tree.

## Root Cause

The migration treated "Node 22 LTS baseline" as an exact major-version ceiling instead of a minimum supported runtime. The Docker verification examples optimized for a clean container context but did not account for filesystem ownership on a shared production server workspace.

## Solution

Changed the package engine range and lockfile root metadata to `>=22`, keeping Node 22 as the minimum while allowing newer LTS runtimes. Updated user-facing docs and AI context to describe "Node.js 22 LTS or newer LTS runtime". Added `--user "$(id -u):$(id -g)"` to Docker verification commands that write into the bind-mounted project directory.

## Prevention

- Runtime baseline migrations should distinguish minimum supported version from maximum allowed version.
- Docker documentation that bind-mounts the repository should specify the invoking user for write-heavy commands such as `npm ci`, build, and tests.
- Reviews should check `engines.node`, lockfile root metadata, docs, and verification commands together.
