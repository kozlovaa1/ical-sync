# Complete Node 22 verification fixes

**Date:** 2026-05-08 14:11
**Files:** `.github/workflows/ci.yml`, `README.md`, `docs/deployment.md`, `package.json`
**Severity:** low

## Problem

Post-implementation verification found minor gaps in the Node 22 migration:

- README Quick Start and deployment docs did not explicitly state the Node 22 LTS runtime baseline.
- `npm test` passed test assertions but could exit non-zero when Vitest tried to write cached result data under a stale `node_modules/.vite` ownership state.

## Root Cause

The migration updated the primary runtime selectors first (`engines.node`, lockfile root metadata, Dockerfile, and CI setup), but supporting verification surfaces were not all synchronized. The test command also relied on Vitest's default result cache, which is sensitive to local filesystem ownership when tests are run through different container users.

## Solution

Updated README and deployment docs to explicitly mention Node.js 22 LTS and `node:22-alpine`. Changed the standard test script to `vitest run --cache=false`, making `npm test` deterministic in the current Docker verification workflow without changing application behavior.

## Prevention

- Runtime migrations should verify both selectors and operator-facing evidence: package engines, lockfile root metadata, CI setup, Docker base images, docs, and runtime-version logging.
- Containerized tests should avoid tool caches that write into shared bind-mounted dependency directories unless ownership is controlled.
- Verification should run the exact standard commands users and CI will run, not only ad hoc command variants.
