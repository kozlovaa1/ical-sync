# Preserve URL path in log sanitization

**Date:** 2026-05-07 21:10
**Files:** src/observability/logger.ts, src/config/env.ts, test/calendar-service.test.ts
**Severity:** low

## Problem

URL sanitization for log metadata returned only the URL origin. The implementation removed query strings, but it also removed the pathname, which did not match the implementation plan requirement to log origin plus pathname.

## Root Cause

The sanitizer treated the origin as the complete safe URL identity. That assumption was too coarse: query strings and fragments can contain secrets and must be stripped, but the pathname is useful non-secret operational context and was explicitly required by the plan.

## Solution

Updated both runtime log sanitization and startup environment metadata sanitization to return `origin + pathname`. Added regression tests that verify query strings and fragments are removed while the path is preserved.

## Prevention

- When sanitizing URLs for logs, explicitly decide which URL components are safe instead of using `origin` as a shortcut.
- Add tests for security-oriented sanitizers that cover both removal of sensitive components and preservation of required operational context.
- During verification, compare implementation behavior against exact wording in the plan, especially for logging and secret-handling requirements.
