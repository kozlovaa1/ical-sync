# URL-safe public token validation

**Date:** 2026-05-07 21:29
**Files:** src/config/env.ts, test/calendar-service.test.ts, test/routes.test.ts, README.md
**Severity:** medium

## Problem

`PUBLIC_TOKEN` was validated only by length, even though the token is embedded in the `/calendar/:token.ics` path. Tokens containing path-sensitive characters such as `/`, `?`, `#`, or non-URL-safe base64 symbols could pass startup validation but produce calendar URLs that are unreliable for clients.

The Traefik setup documentation also mentioned changing only `networks.traefik.name`, while the Compose file also contains a matching `traefik.docker.network` label.

## Root Cause

The original validation assumed that token entropy and length were enough. That missed the transport constraint: this token is not only a secret, it is also a URL path segment. The documentation issue had the same shape: it documented the conceptual setting but not every place where the setting is duplicated in Docker Compose.

## Solution

Added a URL-safe token pattern to environment validation: `A-Z`, `a-z`, `0-9`, `_`, and `-`, with a minimum length of 32 characters. Added regression tests for unsafe and safe tokens, updated existing test fixtures to use URL-safe tokens, and clarified README guidance for both token generation and Traefik network configuration.

## Prevention

- Treat values embedded in URLs as both secrets and URL components; validate format as well as length.
- Add regression tests for config values that cross protocol or framework boundaries.
- When documenting duplicated deployment settings, list every field that must stay in sync.
- Before redeploying stricter secret validation, check existing operator-provided secrets without printing them and plan rotation if needed.
